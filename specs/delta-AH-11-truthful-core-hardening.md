# Delta Spec: AH-11 — truthful-core-hardening

## 1. Intent & Context
- **Issue / Ticket:** AH-11
- **Summary:** An audit of the installed harness found twenty-six defects, and almost every one is the same shape: the harness states something it did not verify. `harness context` reports twelve active delta specs when all twelve are archived and zero are active, and reports zero technical-debt markers because `ripgrep` is absent rather than because the markers are. `harness qa types` exits `0` on a repository with no type checker, so `harness qa all` prints "All required QA gates passed" having checked nothing. `harness sync --check` calls a surface current while fourteen obsolete skills from an unrelated checkout are still published into it. `harness worktree remove wt-AH` matched two worktrees by substring and destroyed an uncommitted file with no prompt. Four documented flags — `--base`, `--module`, `--all`, `--check-auth` — are parsed by nothing. And with no project configuration present, `resolve_config_file` falls through to the repository's own `config.example.json`, so an unconfigured Go project silently runs `pytest`, `ruff`, and `mypy` under a profile named "backend" that its owner never wrote. This delta closes all of it: every advertised claim either becomes executable or stops being advertised.
- **Target Module / Layer:** `core/scripts/lib/config.sh`, `core/scripts/lib/surface.sh`, `core/scripts/lib/debt.sh` (new), `core/scripts/lib/specs.sh` (new), `core/scripts/lib/transaction.sh`, `core/scripts/lib/ai-client.sh` (deleted), `core/scripts/stack-branch.sh`, `core/scripts/stack-commit.sh`, `core/scripts/stack-completion.sh`, `core/scripts/stack-config.sh` (new), `core/scripts/stack-context.sh`, `core/scripts/stack-debt.sh`, `core/scripts/stack-doctor.sh`, `core/scripts/stack-pr.sh`, `core/scripts/stack-qa.sh`, `core/scripts/stack-receipt.sh`, `core/scripts/stack-scan.sh`, `core/scripts/stack-spec.sh`, `core/scripts/stack-worktree.sh`, `bin/harness`, `install.sh`, `schema.json`, `config.example.json`, `rules/landmines.json`, `core/templates/landmines-template.json`, `recipes/*/rules/landmines.json`, `core/skills/doctor/SKILL.md`, `test/test_cli.sh`, `README.md`, `CHANGELOG.md`, `package.json`.

## 2. Requirements & Domain Floor Invariants

### Configuration resolves to something the user wrote
- [x] `resolve_config_file` no longer returns `config.example.json`. A repository with no configuration resolves to no configuration file, which yields the documented built-in defaults, rather than adopting the example's fictional `backend` profile, its `pytest`/`ruff`/`mypy` commands, and its `targetRepoPath` of `~/projects/backend-api`. The example is documentation; it must not be the effective configuration of every unconfigured repository.
- [x] `get_profile_value` distinguishes a configured `false` from an absent key. jq's `//` treats `false` as empty, so today every boolean set to `false` is silently replaced by the caller's default and nothing can be switched off by configuration. The lookup selects the first key that is present rather than the first that is truthy.
- [x] Neither `lib/config.sh` nor `stack-scan.sh` passes a configuration value to `eval`. `targetRepoPath` and `rules.scanner` are expanded for a leading `~` by parameter substitution. Today a configuration file containing a command substitution executes it.
- [x] `harness config validate` reports the resolved configuration file, the active profile and how it was resolved, and every structural problem it can determine: invalid JSON, a non-object `profiles`, a profile key whose type contradicts `schema.json`, an unknown key, a `targetRepoPath` that does not exist, and a `defaultProfile` naming no profile. It exits non-zero when any of those is an error.
- [x] `harness config validate` states which checks it could not perform. It is a structural validator written in jq, not a JSON Schema implementation, and it says so rather than letting "validated" be read as "conforms to `schema.json`".
- [x] The `localAI` block is removed from `schema.json` and `config.example.json`, and `core/scripts/lib/ai-client.sh` is deleted. The library is sourced by nothing, so it has never run; its configuration lives at the schema's top level while `get_profile_value` only reads `.profiles[…]` and `.project`, so it could not have been enabled even by a user who tried. `harness doctor` stops probing for `ollama` and stops requiring `curl`, which no reachable code path uses.

### Required gates fail closed
- [x] `harness qa lint` and `harness qa types` never exit `0` without running a checker. The `ruff check . 2>/dev/null || npm run lint 2>/dev/null || echo 'No linter configured'` default ends in an `echo`, so a repository with neither tool passes both gates. **Amended during implementation.** The original wording had the gate resolve a checker from the tools present on the machine. That was dropped: guessing is what produced the defect — a repository with `ruff` installed but no configuration was linted by a tool the project never chose, and a Go repository was tested with `pytest` for the same reason. A gate with nothing configured for it now simply refuses, names the configuration key to set, and exits non-zero. A project that genuinely has no linter records that as a decision with `"lintCommand": false`, which reports as *declared absent* and does not fail the suite — and is the reason a configured `false` has to survive a lookup at all. The same rule is applied to `qa test` and `qa tdd`, which were guessing `pytest` on the same basis.
- [x] `harness qa all` distinguishes a gate that failed from a gate that could not run, names each in its summary, and exits non-zero for either. "Could not run" is not a pass; `rules/floor.md` invariant 1 does not admit a third outcome that prints success.
- [x] `harness scan` exits non-zero when `jq` is absent instead of skipping the rule loop and printing "passed with 0 errors". This was recorded as a deferred open question in AH-9 and is the same fail-open shape as the four gates AH-9 closed.
- [x] `harness ship` stops on a failed `git push`. Today the push is run as `git push … 2>/dev/null || log_warn "Push skipped or branch already up to date."`, which turns a rejected non-fast-forward, a missing remote, and an authentication failure into a warning and then opens a pull request for a branch that was never pushed. A push that fails aborts before the pull request step and reports git's own stderr.
- [x] `harness commit check` exits non-zero when the inspected message does not conform. A subcommand named `check` that only ever warns cannot be used as a gate, which is the only reason to have it.

### Reported signals match what the commands they mirror report
- [x] `harness context` counts the same active delta specs as `harness spec status`. Both read the same helper, so the two can never disagree again; today `context` finds twelve by recursing into `specs/archive/` while `spec status` correctly finds none.
- [x] `harness context` counts debt markers through the same scan as `harness debt`, and reports `null` in JSON and `unavailable` in text when the scan could not complete. Reporting `0` for "ripgrep is missing" is indistinguishable from `0` for "there is no debt", and it is the count an agent is told to trust. **Amended during implementation.** The shared scan does not fall back from `ripgrep` to `grep`; it drops `ripgrep` entirely and reads tracked files through `git grep`. A fallback would have preserved the real divergence underneath the bug — `ripgrep` honours `.gitignore` and `grep -r` does not, so the same tree answered differently depending on which tool was installed, and `grep -r` additionally walked `.git`. `git grep` needs no dependency the harness does not already require and gives one answer everywhere. Completion is judged on stderr as well as the exit status, because `git grep` reports an unreadable file as a diagnostic and still exits `1`, its code for "no match".
- [x] `harness context --json` is emitted by `jq`, so a repository path, branch name, or profile containing a quote or a backslash produces valid JSON rather than a broken document assembled by a heredoc.
- [x] `harness doctor` performs the three checks `core/skills/doctor/SKILL.md` already claims for it: the CLI symlinks in `~/.local/bin` resolve to this checkout and their directory is on `PATH`; the target repository's `pre-commit` hook is agent-harness's own, a foreign hook, or absent; and the resolved configuration passes `harness config validate`. Either the checks exist or the claim stops being made, and the checks are worth having.
- [x] `harness doctor --check-auth` reports the authentication state of the configured issue and CI provider CLIs. It is currently advertised, parsed, assigned to a variable no check reads, and marked in the source with its own `# defer:` debt marker.

### Destructive commands say what they will destroy
- [x] `harness worktree remove <key>` matches a worktree by exact issue key or exact path, never by unanchored substring. `harness worktree remove wt-AH` removed both `wt-AH-1` and `wt-AH-2` in a reproduction, because the key was interpolated into `grep` as a pattern and every match was removed.
- [x] `harness worktree remove` names every matching worktree before removing anything, refuses to act when the key matches more than one, and refuses to remove a worktree with uncommitted changes unless `--force` is given. It no longer passes `--force` to `git worktree remove` unconditionally; the reproduction destroyed an unsaved file with no prompt and no way to recover it.
- [x] `harness worktree remove --dry-run` reports what would be removed and mutates nothing.
- [x] `./setup` with no arguments asks for confirmation before installing, and names the two destinations it will write to: the global surfaces and the current directory. It is advertised as a "Guided interactive installer" and asks nothing today, so running it from `$HOME` installs `AGENTS.md`, a `CLAUDE.md` and `GEMINI.md` symlink, `stack.config.json`, `rules/`, and four skill surfaces into the home directory. With no controlling terminal it refuses and names the explicit flag to use instead, so scripted and agent invocations fail closed rather than hang.
- [x] `./setup` refuses to initialize a directory that is not a Git repository. Every workflow the installed surface describes — branches, worktrees, specs, receipts, ledgers, scans — requires one. **Amended during implementation.** The refusal applies to the guided path, where the directory is inferred; an explicit `--target <path>` is a deliberate choice and is warned about rather than refused. Refusing it would have broken eighteen existing installer tests that initialize plain temporary directories on purpose, and would have added no safety: the hazard in the audit was `./setup` inferring `$HOME`, not a user naming a path.
- [x] Committed transaction journals are pruned to the ten most recent, oldest first, after each commit. Each journal holds a full backup of every file the installation replaced and nothing has ever removed one.

### Advertised flags are parsed
- [x] `harness branch create` and `harness worktree create` accept `--base <branch>`. Both advertise it and both read the base from the fourth positional argument, so `harness branch create feat AH-99 demo --base main` passes `--base` to `git checkout -b` as a revision and prints git's usage text instead of creating a branch.
- [x] `harness spec create` accepts `--module <name>`. **Amended during implementation.** Filing the spec under `specs/<module>/` would put it outside the one place both `spec status` and `context` define as active, so the module is recorded in the spec instead, as a `- **Module:**` line, and `harness spec archive` reads it back when no module argument is given. The flag now changes something real without contradicting the definition of "active" this delta makes canonical.
- [x] The debt marker pattern also recognizes `//` comments. The marker is documented as `# pragmatism:`, and two of the three shipped recipes are for languages where no comment begins with `#`, so debt harvesting could not work in a TypeScript or Go project at all. **Added during implementation**, from the same audit finding as the `--all` flag below.
- [x] A run of `./setup` that names only modifiers — `--yes`, `--expert`, `--recipe <name>` — performs the guided installation rather than selecting no action and reporting success. **Found during implementation** of the guided confirmation: guided mode was keyed on `$# -eq 0`, so adding the `--yes` flag that confirms it also disabled it, and the run printed "Setup complete!" having written nothing. Guided is now the default scope, which is what the usage text has always said.
- [x] `harness debt` accepts `--all` and `--path <path>`, and `harness debt --json` emits a single JSON array. Today `--all` is advertised and dropped, and `--json` emits either a human log line or `ripgrep`'s JSON-Lines stream, neither of which any consumer can parse — and the `harness-implement` and `harness-fix` bundles both instruct agents to call it.
- [x] `harness spec status --json` emits the active delta specs as a JSON array. The flag is advertised in the dispatcher help and was dropped along with every other argument, so the JSON form printed the human listing. **Found during review** of the help text against the implementation, in the same class as `--module` and `--all`.
- [x] The dispatcher help lists `orchestrate` among the workflows `harness receipt start` accepts. It has accepted it since AH-7 and the help named only three. **Found during review.**
- [x] `harness completion install` installs a Bash completion alongside the Zsh one, and both complete the current command list. `README.md` advertises "Shell Autocompletion (Zsh & Bash)" and `stack-completion.sh` writes only `_harness` for Zsh.
- [x] `harness --profile` with no value exits non-zero naming the missing argument. It currently runs `shift 2` with one argument remaining, which under `set -e` exits `0` having done nothing.
- [x] `harness spec create` rejects an issue key or slug containing a path separator or a `..` segment. `harness spec create AH-1 a/b` currently reaches `sed` and fails with a raw redirection error naming a path outside `specs/`.
- [x] `harness init --recipe <unknown>` exits non-zero and names the available recipes. It currently tests `[ -d "recipes/${recipe}" ]`, silently installs no recipe, and reports success.
- [x] `harness commit build` anchors its issue-key extraction to the branch's issue segment. `feat/add-2fa-support` currently yields `feat(add-2)`, because the pattern `[A-Za-z0-9]+-[0-9]+` matches anywhere in the branch name. **Superseded during merge.** AH-12 landed the same fix on `main` first and shipped it in 2.4.2, requiring an uppercase prefix and digits not followed by a dot. That implementation is the one kept: it is released, it carries its own test group, and the only behaviour this delta's version added beyond it was accepting a lowercase key, which nobody asked for. The one case AH-12's group does not reach -- a lowercase slug carrying a digit -- is kept as an assertion here.
- [x] `harness commit build` refuses to commit when nothing is staged, instead of invoking `git commit` and surfacing git's own error after printing a success-shaped "Generated commit message" line.

### Drift detection sees everything that is published
- [x] `surface_evaluate` reports a managed skill that the surface publishes but the manifest does not record. A directory carrying `.agent-harness-managed`, or a symlink into any checkout's `core/skills/`, that is absent from the manifest is drift. In the audited installation fourteen such entries — including `ship`, which the catalog marks `removed` — were published into `~/.claude/skills` from a second checkout while `harness sync --check` called the surface `current`.
- [x] `remove_managed_skill` recognizes a managed symlink by its shape rather than by its target's prefix. It matches only `${HARNESS_ROOT}/core/skills/*` today, so a surface installed from one checkout can never be repaired by another, which is how those fourteen entries became unreachable to every later run.
- [x] `test/test_cli.sh` isolates `HOME` for its doctor group. **Found after implementation**, by noticing that the fourteen stale skills the audit reported in `~/.claude/skills` had already been removed from the real machine: the group has run `harness doctor --fix` without isolating `HOME` since AH-10, and `doctor --fix` repairs the global scope as well as the repository one. The suite may not reach outside its temporary directory, and a test whose subject is repairing surfaces has to be held to that hardest.
- [x] `harness sync` removes those entries and reports each removal by name. Repair means the surface ends up as the catalog describes it, and a stale skill competing with its namespaced replacement in an agent's skill list is exactly the failure the manifest exists to prevent.

### The scanner can be pointed at paths and argued with
- [x] A rule may carry `pathPattern` instead of `pattern`, matching the repository-relative path rather than file content. The scanner has no way to express a forbidden *filename* today, so it cannot block `.env`, `*.pem`, `*.key`, or a committed agent directory — which is the first thing a pre-commit gate is installed to stop.
- [x] The shipped rules and the template gain `SEC-003`, refusing environment files, private keys, and certificate bundles by path.
- [x] A finding is suppressed by `harness-ignore: <RULE-ID>` on the matching line or the line above it, and a rule may carry `excludePaths` globs. Without an escape hatch a single false positive leaves `--no-verify` as the only option, which retires the gate entirely rather than for one line.
- [x] Each recipe ships the `rules/landmines.json` its `stack.config.json` already points at. All three declare `rules.scanner: "./rules/landmines.json"` and none provides one, so a TypeScript or Go project initialized from a recipe inherits the Python template's `.objects.all()` and `cursor.execute(f"` rules and is scanned for defects it cannot have.

### Receipts can be read
- [x] `harness receipt list` reports every run with its workflow, issue, branch, start time, and whether it is terminal. `harness receipt show <run_id>` prints one run's events. The receipt command has been write-only since AH-3: the observability record it exists to produce cannot be read back by the user it was produced for.
- [x] `harness receipt prune` removes terminal receipts and reports the count. Non-terminal receipts are never pruned; an abandoned run is a finding, not litter. **Amended during implementation.** Retention is by count (`--keep`, default 50) rather than by age. An age window needs date arithmetic on the receipt's own ISO timestamp, and `date -d` versus `date -j -f` is the one portability difference between the two CI runners this delta would otherwise have introduced. Count-based retention is also the idiom the transaction journals in this same delta already use.

### Invariants
- [x] Invariant: the change must not violate `rules/floor.md`.
- [x] Invariant: no new runtime dependency. Bash, Git, `grep`, `sed`, `awk`, and the already-required `jq` only.
- [x] Invariant: shell stays portable across the macOS and Ubuntu CI runners. No GNU-only flags for `grep`, `sed`, `find`, `stat`, `date`, or `mktemp`.
- [x] Invariant: every changed script passes `shellcheck -S warning` through `npm run lint`.
- [x] Invariant: the scanner's exit contract is unchanged — `0` means no error-level findings, `1` means findings or an unusable ruleset — so the installed pre-commit hook needs no migration.
- [x] Invariant: `harness receipt start|phase|finish` keeps its schema and its stdout contract, so a workflow already recording a run is unaffected by the new read path.

## 4. Verification & QA
- **Automated Test Command:** `env -u STACK_PROFILE npm test && npm run lint && ./setup --verify`
- **Pre-flight Command:** `./bin/harness qa all`
- **Spec Verification:** `./bin/harness spec verify specs/delta-AH-11-truthful-core-hardening.md`
- **Expected Outcome:** The nine new groups pass, the existing twenty-three stay green, the transaction and installer suites stay green, `shellcheck -S warning` is clean, and CI passes on both runners.

## 5. Non-Goals
- Full JSON Schema validation of the configuration. `harness config validate` performs the structural checks jq can express and reports what it did not check; adding a schema engine would add the first runtime dependency beyond Bash, Git, and jq.
- A rule schema beyond `pathPattern`, `excludePaths`, and inline suppression. Severity models, rule inheritance, and multi-line matching stay out.
- Reworking the `qa` command surface. This delta changes when a gate refuses to report success, not which gates exist or how they are named.
- A ledger read path beyond the `show` and `rulings` it already has, and any change to the receipt event schema.
- Chained pre-commit hooks. Doctor learns to report a foreign hook; making two hooks coexist is a design, not a diagnostic.
- Repairing the fourteen stale skills found in the audited installation by hand. The fix is that `harness sync` can now remove them; running it is the user's call.

## 6. Open Questions
- **This delta bundles what AH-9 deliberately separated.** AH-9's non-goals list is, almost item for item, the defect list above, on the stated grounds that bundling them would make the diff unreviewable under `rules/floor.md` invariant 6. The user has asked for all of it in one pass. The mitigation is structural rather than rhetorical: the requirements are grouped by seam, each group gets its own RED test group and its own commit-sized slice, and no group depends on another's implementation. If review finds the diff unreviewable anyway, the groups split cleanly along those boundaries.
- **Removing `config.example.json` from the resolution order is a behavior change for existing installations.** A repository that has been relying on the example's `backend` profile — knowingly or not — will resolve to built-in defaults after this change, and its `harness qa` commands will stop running `pytest` unless it writes the configuration it was implicitly borrowing. That is a corrected defect rather than a regression, but the CHANGELOG entry must say plainly that an unconfigured repository's QA commands change.
- **Release numbering.** 2.4.1 was the last release, and this changes the outcome of gates that previously passed, adds commands, and removes a configuration block. It is cut as `2.5.0`, and the CHANGELOG entry leads with the two changes that can turn a green run red: the fail-closed lint and type gates, and the loss of the example-configuration fallback.
- **AH-11 was already used once.** Commit `65fcca2` is `docs(AH-11): record context-mode as complementary tooling`, a documentation-only change with no spec. The token is reused here at the user's explicit direction; the history will show one AH-11 docs commit predating this delta.
